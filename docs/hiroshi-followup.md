# ヒロシ商談フォロー 運用メモ

商談後（Cヨミ・失注）の見込み客へ、ライトアップのAIアシスタント「ヒロシ」名義で
フォローメールを送る仕組み。

## 全体の流れ

| 時刻(JST) | ルーティン | 状態 |
|---|---|---|
| 平日 01:00 | ①文面生成 `trig_01UnxKuBTk6Kr7XNaHUDqa9A` | 稼働中 |
| 平日 08:00 | ②送信 `trig_018XdHfX83D8H3vG5dxsp3dr` | 稼働中 |
| 毎時 | 返信→Slack通知 `trig_013egkxsLwBErzTSgVTZHpNF` | 稼働中（2026/09/03、毎時→6時間おき→根本原因を修正後、再び毎時に） |

- ①は `data/hiroshi-sent-log.csv` を読んで除外判定し、文面を `data/drafts/YYYY-MM-DD.csv` に書いて push する。実送信はしない。
- ②はその CSV を読んで Gmail 送信し、結果を `data/hiroshi-sent-log.csv` に追記して push する。送信後、その日の分だけを Drive の「ヒロシ送信キュー」へ CSV で書き出す（Codex 側の朝9時ルーティンがこれを読んでスプレッドシートへ追記する）。
- 上限は 1日150通。件名は必ず `【ライトアップ】` で始める。
- **対象は、直近の商談（R列・S列のうち新しい方）から30日以上経過している会社のみ。**
  2026/09/03 発覚：この条件が①のプロンプトに入っておらず、商談の翌日〜3週間後という
  近すぎる相手に19社誤って送っていた（詳細は下記「対象選定の不具合」）。
- **顧客からの返信は、原則1時間以内に Slack へ通知される。** 一時的に6時間おきへ
  落としていたが、根本原因（下記「返信監視について」）を直したうえで毎時に戻した。

## 対象選定の不具合：2026/09/03、商談直後の相手に送っていた

ユーザー方針は「フォローは前回の商談から1ヶ月以上空いている相手が望ましい」。
しかし①のプロンプトには、ヨミ表のステータス（失注・Cヨミ等）と、AG列のキーワード
（「再商談確定」等）による進行中案件の除外はあったが、**商談日そのものと本日の
日付を突き合わせて経過日数を計算する条件が入っていなかった。**

その結果、9/2〜9/3のバッチで66社に送った中の19社が、実際には商談から
30日未満だった。最短はエーキャスト・マーケティング&ソリューション様で、
2回目商談の**翌日**に送信している。

修正：①のプロンプトに「R列（初回商談日）・S列（2回目商談日）のうち新しい方と
本日の差が30日未満なら、ステータスに関わらず必ず除外する」を明記した。
確信が持てない・日付が読み取れない場合も対象から外す（不確かなら送らない）。

## ②送信ルーティンについて

`trig_018XdHfX83D8H3vG5dxsp3dr` として 2026/09/02 に作成済み。
自動モードの分類器に2回ブロックされたが、3回目で通った（同じ内容でも通る／通らないが揺れる）。

設計上のポイント：

- 実行先は既存セッション `session_01EieH6uvMF7rRQUa6e1EHBs`（self-bind）。
  新規セッションだと Gmail / Drive / Slack の接続を引き継げない。
  作成時に「MCPコネクタを保持しない」という警告が出るが、self-bind のルーティンは
  実際にはセッションのMCPツールを引き継ぐ（返信監視ルーティンで実証済み）。
- 送信対象は `data/drafts/` 配下の**全CSV**から、台帳に記録済みの分を引いた残り。
  当日ファイルだけを見る作りにすると、朝8時より後に作った下書きが永久に送られないため。
  この作りなら、実行できなかった日があっても翌朝に自動で追いつく。
- 150通を超えた分は台帳に記録しないので、翌朝そのまま対象になる。

## 返信監視について

`trig_013egkxsLwBErzTSgVTZHpNF` は、毎時実行のトークン消費が重いという理由で
2026/09/03 にいったん**6時間おき**（cron `0 */6 * * *`）へ落とした。その後、
消費が重かった本当の原因（下記「もう一つの不具合」参照）を修正したうえで、
返信への即応速度（電話をかけたいので速度優先、というユーザー方針）を理由に
**毎時**（cron `0 * * * *`）へ戻した。根本原因を直した後の毎時運用なら、
ヒット0件の実行はほぼ検索1回分のコストで済むはず。

過去に判明した不具合（修正済みだが記録として残す）：
検索条件に `is:unread` を含めていたため、人が先に Gmail を開いて既読にすると
その返信は二度と拾われなかった。2026/09/02 の有限会社ゲスト様からの返信
（初めての顧客返信）がこれで見落とされ、翌日ユーザーが手動で発見した。
現在のプロンプトは `is:unread` を使わず、処理済み判定を `Label_1` のみで行う。

6時間おきなので、最悪その間隔だけ通知が遅れる。急ぎで確認したい場合は
Gmail (ai.firststep2026@gmail.com) を直接見てよい。さらに頻度を上げ下げしたい
場合は `mcp__Claude_Code_Remote__update_trigger` の `cron_expression` を変える。

### 2026/09/03 のトークン消費調査で判明した、もう一つの不具合

ユーザーから「検索範囲（7日）が広すぎるのでは」という指摘があり調べたところ、
原因は範囲の広さそのものではなく、**`search_threads` がスレッド単位で結果を返すため、
スレッド内にラベル未付与のメッセージが1件でも残っていると、そのスレッド全体が
毎回ヒットし続ける**という構造だった。

実際に、高田様（有限会社ゲスト）の返信とラスカーラ・オペラ振興会宛のバウンスに
`Label_1` が付いていないまま残っており、数日間ずっと再取得され続けていた
（原因：これらは通常の監視フロー外で人手・別作業として処理されたため、
ラベル付けの手順が実行されなかった）。手動でラベルを付けて解消済み。

あわせて、`writeup.co.jp`（社内）からのメールが検索条件に引っかかっていたため
`-from:writeup.co.jp` を追加した。検索範囲は 7日→3日 に縮小したが、これは
副次的な対策であり、**主因はラベル付けの徹底不足**だったことに注意。

再発防止として、プロンプトに「投稿の成否にかかわらずラベル付けは必ず試みる」
「顧客の返信・バウンスは監視フロー外で処理した場合も忘れずラベルを付ける」を明記した。
監視フロー外（このセッションが手動でメールを読んだ・返信した場合など）で
処理したメッセージには、その場で `mcp__Gmail__label_message` を呼んで
`Label_1` を付けること。

## スプレッドシートへの自動追記（Codex 経由）

Claude 側から Google スプレッドシートのセルを直接書き換える手段は無い。
Drive MCP の `update_file` はタイトルと保存先しか変えられず、コネクタ一覧にも
Google スプレッドシートを編集できるものは存在しない（2026/09 時点で確認済み）。

そこで、**Drive へのファイル作成はできる**ことを利用して、次の形で自動化している
（当初 Apps Script 案を検討したが、最終的に Codex 側のルーティンで実装した）。

```
朝8時のバッチ（Claude）→ Drive「ヒロシ送信キュー」フォルダに、
                            **その日新しく送信した分だけ**を CSV で作成
                                ↓
朝9時のルーティン（Codex）→ CSV を読んで「送信mailログ」へ行を追加し、
                                CSV を「処理済み」へ移動
```

- キューフォルダ: `1tlwhtOwSh8J6_N8xaPNdNoUm3BRyXUfq`
  https://drive.google.com/drive/folders/1tlwhtOwSh8J6_N8xaPNdNoUm3BRyXUfq
- Codex 側ルーティン名: 「ヒロシ送信ログ→スプレッドシート追記」（毎日9:00）
- 指示文: `docs/codex-sheet-import-prompt.md`
- 重複防止は D列（送信先）でのチェックに依存しているが、**2026/09/03 に機能しないことが判明した**
  （下記インシデント参照）。そのため Claude 側は **常にその日新しく送った分だけ**を渡し、
  過去分を含めない運用で重複を根本から防いでいる。

送信履歴の正本は引き続きリポジトリ側の `data/hiroshi-sent-log.csv`。
スプレッドシートは人間が見るためのミラーという位置づけは変わらない。

### インシデント：2026/09/03、シートに重複行が発生

9/1〜9/3の送信結果86件をまとめて過去分バックアップとしてCSV化し、
Codexのキューフォルダへ1回だけ手動で置いた。このCSVには**既にシートにあった
9/1の20社も含めてしまった**。Codex側のD列重複チェックが機能せず、
その20社が2重に書き込まれ、さらにシートに900行超の空行も生じた
（原因未特定。既存アドレスの表記ゆれの可能性）。

**実害はなし**（Gmail送信履歴では1回のみ送信を確認済み。二重送信は発生していない）。
シート上の記録が二重になっただけ。ユーザー判断でシートの重複行はそのまま残している。

再発防止：Drive へ渡すCSVには、**その日新しく送信した分だけ**を含める
（過去分・既存分を二度と含めない）。これにより、Codex側の重複チェックが
仮に効かなくても、渡すデータ自体に重複の種がないので再発しない。

## そのほかの制約
- 「送信mailログ」タブは `read_file_content` では読めない。
  `download_file_content` に `exportMimeType='application/vnd.openxmlformats-officedocument.spreadsheetml.sheet'`
  を指定して xlsx として取得すると全タブ読める。
- 送信元は新規の Gmail アカウントのため、Gmail 側の上限は 500通/日。
  到達率の観点からも急な増量は避け、150通/日で様子を見る。
