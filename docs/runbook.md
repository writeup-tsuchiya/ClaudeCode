# 運用手順書

## 1. 日次の流れ

| 時刻 | 誰が | やること |
|---|---|---|
| 17:00 | 自動 | Routineが発火。翌営業日のアポを抽出し、Gmail下書きと架電リストを生成 |
| 17:00-17:10 | 当番1名 | Gmailの下書きフォルダを開き、宛先と文面をざっと確認して送信 |
| 17:10-17:40 | 各担当 | 架電リストのP1（3〜5件）に電話 |
| 翌朝 | 各担当 | 顧客からの日程変更返信があれば対応（Ccに入っているので担当にも届く） |

土日祝が挟まる場合、Routineは日〜木に発火し、翌営業日を自動で対象にします。
（金曜17時に発火して土曜を対象にする、という無駄打ちが起きないようにしてあります。）

## 2. Routineの管理

- 発火設定：`0 8 * * 0-4`（UTC）＝ 日〜木 17:00 JST
- 停止したいとき：Claudeに「前日リマインドのRoutineを止めて」と言えば無効化されます。
- 時刻を変えたいとき：「リマインドのRoutineを18時に変えて」等。UTC変換は自動でやります。
  `config/team.json` の `schedule` も併せて更新してください（記録用）。

## 3. 自動送信への切り替え

`config/team.json` を編集：

```json
"delivery": {
  "autoSend": true
}
```

**切り替える前に確認すること：**

1. 2週間分の下書きを見て、宛先ミス・空欄・文面崩れが0件だったか
2. 顧客から「メールの内容が違う」という指摘が来ていないか
3. 手動対応（顧客情報なし）の件数が減っているか

`autoSend: true` にしても、以下のいずれかが1件でもあれば **その日は送信せず停止して報告** します：
- 宛先が `@writeup.co.jp` になっている（社内アドレスへの誤送信）
- 会社名が空
- 同じ宛先に複数通

## 4. 送信元アカウントの本番構成

現状、Gmailコネクタは `aizawa@writeup.co.jp` で認証されており、**下書きはこのアカウントにしか作れません**（Gmail APIの仕様）。

選択肢：

| 案 | 内容 | 評価 |
|---|---|---|
| **A. 現状維持** | `aizawa@` から送信、Ccに担当営業、署名は担当営業名 | すぐ動く。ただし顧客から見ると担当と差出人が違う |
| **B. 部の共通アドレスを作る**（推奨） | 例 `sales1@writeup.co.jp` を作りコネクタを繋ぎ直す。「第一営業部」名義なので差出人の違和感が消える | 本番運用ならこれ。Workspace管理者に依頼が必要 |
| C. 各営業のアカウントで個別に接続 | 6セッション分の接続が必要。1つのRoutineから6アカウントには書けない | 現実的でない |
| D. Google Workspaceのドメイン全体委任 | サービスアカウントで各営業名義の送信が可能 | 実装が別途必要。将来的な選択肢 |

**Bに切り替える手順：** 共通アドレスを作成 → Claude側でGmailコネクタをそのアカウントで接続し直す → `config/team.json` の `senderAccount.address` を更新。

## 5. トラブルシュート

**アポが0件になる**
カレンダーの共有権限が切れている可能性。`list_calendars` に6名が出るか確認する。
`accessRole` が `reader` 以上であれば読める。

**社内MTGにメールが作られた**
`config/team.json` の `exclude.titleContains` にそのタイトルを追加する。

**顧客アポなのに除外された**
`exclude` のキーワードに引っかかっている。`訪問` `NT` などは短く誤爆しやすいので、
誤爆する場合は `titleContains` から外して `titleExact` 側に移す。

**要架電が10件を超える**
`callPriority.earlyMorningBefore` が遅すぎるか、`titleKeywords` が広すぎる。
まず `earlyMorningBefore` を `"10:00"` に下げて様子を見る。

**手動対応が毎日5件以上出る**
TimeRexを通さず手で予定を入れているケースが多い。
予定作成時に description へ3行（`ゲスト会社名 : ` `ゲスト氏名 : ` `ゲストメールアドレス : `）を書く運用を徹底すると解消する。
テンプレートをカレンダーの説明欄にコピペできる形で共有するのが早い。

**Routineが動いた形跡がない**
Routineは新しいセッションを立ち上げて実行します。そのセッションがこのリポジトリの
**デフォルトブランチ**をcloneするため、`.claude/skills/apo-remind/` がデフォルトブランチに
マージされている必要があります。作業ブランチのままだとスキルが読み込まれません。

## 6. 効果測定

最低限これだけは記録すると、改善の判断ができます。

| 指標 | 取り方 | 見方 |
|---|---|---|
| ドタキャン率 | 週次で「当日不参加 ÷ 全アポ」 | 導入前後で悪化していないか。**これが最重要** |
| 前日リマインド工数 | 当番の実測 | 2時間 → 30分に落ちているか |
| 日程変更の申し出件数 | メール返信数 | 増えていれば良い兆候（当日ドタキャンが事前変更に変わった） |
| 手動対応件数 | 架電リストの⚠欄 | 減っていくべき数字 |

**導入から4週間はドタキャン率を毎週見てください。** 悪化していたら
`callPriority` を緩めて架電対象を増やす（＝電話に戻す）のが正しい打ち手です。
工数削減よりドタキャン率の維持が優先です。

## 7. AI音声架電への拡張

電話そのものを自動化したい場合の論点。**今回は実装していません。**

- 架電リストのP1が、そのまま発信対象リスト（電話番号＋トーク材料つき）になります。
- 候補サービス：IVRy / MiiTel / Twilio + 音声合成。いずれも外部契約と実装が必要。
- 検討すべき点：
  - **留守電時の挙動。** BtoBの前日リマインドは繋がらないことが多く、留守電メッセージの質が成果を決めます。
  - **日程変更の受け方。** AIが「変更したい」を受けたあと、誰にどう引き継ぐか。ここが設計の山場です。
  - **名乗りの扱い。** AIであることを明示するか。明示しない運用は顧客からの信頼を損なうリスクがあります。
- 費用対効果の目安：現状の残工数は架電20分/日 ≒ 月7時間。ここを削るために外部契約と実装を入れる価値があるかで判断してください。
  **先にメール自動化の効果を4週間見てから決めることを勧めます。**
