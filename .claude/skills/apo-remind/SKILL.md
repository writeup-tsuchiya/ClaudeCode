# 前日リマインド自動化（第一営業部）

翌営業日の顧客アポに対して、**メールは全件自動・電話は絞った数件だけ人が対応する**ハイブリッド運用を実行する。
目的は「毎日2時間の前日架電」を「メール確認10分＋架電3〜5件（20〜30分）」に圧縮すること。

## 前提

- アポは TimeRex 経由で各営業のGoogleカレンダーに入る。顧客情報は**イベントの description に平文で入っている**（attendees には入っていないことが多い）。
- Gmail下書きは `config/team.json` の `senderAccount` のアカウントにしか作れない。担当営業は Cc に入れる。

## 手順

### 1. 設定を読む

`config/team.json` を読む。以下は必ずこのファイルの値を使い、ハードコードしない。

- `members[]` … 対象カレンダー6件と担当者名
- `delivery.autoSend` … false なら下書きまで、true なら送信まで
- `callPriority` … 架電要否の判定条件
- `exclude` … 社内予定の除外条件

### 2. 対象日を決める

- 指定がなければ **実行日の翌日**。
- 翌日が土日祝（`ja.japanese#holiday@group.v.calendar.google.com` を確認）なら、**次の平日**を対象にする。
- 対象日を `YYYY-MM-DD（曜日）` の形で最初に明示すること。

### 3. カレンダーから予定を取得

`members[]` の各 `calendarId` について `list_events` を呼ぶ。6件は**並列で実行する**。

```
calendarId: <各メンバー>
startTime:  <対象日>T00:00:00+09:00
endTime:    <対象日の翌日>T00:00:00+09:00
timeZone:   Asia/Tokyo
orderBy:    startTime
pageSize:   50
```

### 4. 顧客アポを抽出・重複排除

抽出と正規化の詳細ルールは `references/extraction.md` に従う。要点：

1. `exclude` に該当する社内予定を落とす。
2. 残った予定の description から顧客情報（会社名／氏名／メール／電話／業種／課題／紹介コード／お電話口担当／Meet URL）をパースする。
3. **重複排除**：同じアポが複数メンバーのカレンダーに現れる（同席案件）。`event.id` が同一なら1件に統合し、**担当営業＝`organizer.email` に対応するメンバー**、同席者は補足として保持する。
4. `status` が `cancelled` の予定は除外する。

抽出できた件数と、**顧客情報が取れず手動対応になる件数**を必ず報告する。

### 5. 架電優先度を判定

`config/team.json` の `callPriority` に従い、各アポを **P1（人が架電）** か **P2（メールのみ）** に振り分ける。
以下のいずれかに当たれば P1：

- 顧客メールアドレスが取得できない（`noEmailAddress`）
- 開始時刻が `earlyMorningBefore` より前（朝イチ枠は失念リスクが高い）
- タイトルに `titleKeywords` のいずれかを含む（来社・訪問・重要案件★・キックオフ・納品・リスケ・2回目以降）
- 顧客メールが `manualAlwaysCall` に載っている

それ以外はすべて P2。**P1が6件を超えたら判定条件が緩すぎるサインなので、その旨を報告に添えること。**

### 6. リマインドメールを作成

P1・P2 を問わず、**メールアドレスが取れた全アポ**についてメールを作る。
文面は `references/mail-templates.md` のテンプレートを商談種別に応じて選び、顧客情報で埋める。

- `to`: 顧客メールアドレス
- `cc`: 担当営業の `cc` アドレス（`delivery.ccAssignedRep` が true のとき）＋ `delivery.ccAdditional`
- `subject` / `body`: テンプレートに従う

`delivery.autoSend` が:
- **false** → `mcp__Gmail__create_draft` で下書きを作成する。**絶対に送信しない。**
- **true** → 送信する。ただし送信前に、宛先・件名・担当者名の対応表を一覧で提示し、明らかな異常（宛先が @writeup.co.jp になっている／会社名が空／同一宛先の重複）が1件でもあれば送信を中止して報告する。

メールアドレスが取れなかったアポは下書きを作らず、架電リストに回す。

### 7. 架電リストを出力

`references/call-list.md` の書式で、その日の成果物として出力する。内容は：

- 対象日と全アポ件数
- **P1：人が架電する先**（時刻／担当／会社名／氏名／電話番号／理由／トークの要点）
- P2：メール送付済み（下書き作成済み）一覧 — 確認用に時刻・担当・会社名・宛先だけの一覧
- 手動対応が必要なもの（顧客情報が取れなかった予定）

架電リストは**担当営業ごとにグルーピングして**出す。各自が自分の欄だけ見れば済むようにするため。

### 8. 完了報告

最後に必ず、この4つの数字を1行で報告する：

```
対象日 8/4（火）｜全アポ N件 ｜ 下書き作成 N件 ｜ 要架電 N件 ｜ 手動対応 N件
```

## やってはいけないこと

- `delivery.autoSend` が false のときに送信すること。
- 顧客情報を推測で埋めること。description に無い電話番号・役職・課題を創作しない。取れなければ「不明」と書く。
- 社内MTG（全件壁打ち会・第一の営業MTG等）に対してメールを作ること。
- 架電リストに「全件架電」と書くこと。絞るのがこの仕組みの目的である。
